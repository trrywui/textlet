## 1. 已确认的问题

### P1：恢复上一代快照后，自动清理删除仍可救回的新草稿

触发条件：当前 `session.json` 损坏，但它引用的较新 `.txt` 正文仍完整；上一代快照可以读取。

复现步骤：

1. 保存正文 `older body`，再保存 `NEWER RECOVERABLE BODY 中文🙂`，产生两代快照和两个正文修订。
2. 只在当前清单末尾添加非法内容，保留两个正文文件。
3. `SessionStore.load()` 成功回退，归档损坏的清单；此时较新正文仍存在。
4. 模拟应用启动后的 `saveSession()`：较新正文被当作未引用文件删除。

实际结果：恢复了 `older body`，损坏清单被归档，但 `NEWER RECOVERABLE BODY 中文🙂` 所在文件从磁盘消失。原先可通过人工检查找回的正文也被删除了。

原因：恢复流程只归档清单；随后的清理仅保留当前、上一代清单引用的正文，没有保留损坏快照的正文修订。

代码位置：[恢复与归档](/Users/lee/workspace/code/textlet/Sources/Session.swift:180)、[草稿清理](/Users/lee/workspace/code/textlet/Sources/Session.swift:236)。

建议：恢复时隔离保存相关正文，或在恢复后暂停清理未引用修订。回归测试应检查“可读的新正文仍被保留”，不能只检查旧正文成功恢复。

证据：[完整探针结果](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/pure/final-results/pure-probes.json)。`newerBodyExistsBeforeStartupSave=true`，`newerBodyExistsAfterStartupSave=false`。

### P2：等长且保持时间戳的外部替换没有显示变化

触发条件：文件内容被外部程序替换，但字节数与修改时间保持不变。备份恢复、保留时间戳的复制等操作可能形成这种状态。

复现步骤：

1. 打开正文为 `AAAA` 的文件，记录其原始纳秒级修改时间。
2. 原子替换为 `BBBB`，通过 `utimensat` 恢复原始时间戳。
3. 等待真实文件监听回调，检查标签与状态栏。

实际结果：磁盘摘要已经变化，但 `fileChangedExternally=false`、`needsFileSave=false`，状态栏仍显示“文件已保存”。独立模型测试和 GUI 测试均复现。

原因：文件监听能够区分 inode、ctime 等变化，但 `Note.refreshFileState()` 最终只比较 mtime 和大小，因此丢弃了这些变化信息。

代码位置：[状态判断](/Users/lee/workspace/code/textlet/Sources/Session.swift:67)、[监听签名](/Users/lee/workspace/code/textlet/Sources/DocumentFile.swift:178)。

建议：在监听检测到文件身份或内容相关事件后复核磁盘版本，必要时将摘要计算放到后台，并防止过期结果覆盖新状态。避免每次应用激活时在主线程重新扫描所有文件。

这是状态提示问题。本轮代码检查确认显式保存仍会比较磁盘摘要并进入冲突处理，不能据此断言保存会静默覆盖外部内容。

证据：[独立模型测试](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/pure/final-results/pure-probes.json)、[真实监听与状态栏结果](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/gui-stable/result.json)。

## 3. CPU / 内存基线

条件：macOS 14.8.9、Intel、Swift 6.0.3；1680×940pt、2× Retina；240 行中英文混合文本，初始 36,611 个 UTF-16 单元；20 次操作/秒；每轮 160 次键盘输入、160 次实际移动视口的滚动，每 20 次滚动换向。每轮新进程、新会话。正式成绩未并行编译、运行其他测试或采集调用栈。

CPU 使用本进程 user + system 时间，100% 表示一个核心。内存为 `TASK_VM_INFO.phys_footprint`，不是 RSS，也不包含 WindowServer、输入法或 GPU 的独立占用。空闲值包含测试采样器成本。

| 条件 | 输入 CPU | 滚动 CPU | 输入后空闲 CPU | 滚动后空闲 CPU | 滚动采样内存峰值 | 进程物理占用历史峰值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 默认 32MiB 缓存，第 1 轮 | 23.71% | 26.49% | 0.226% | 0.279% | 93.64MiB | 124.54MiB |
| 关闭屏外缓存，对照 1 轮 | 23.66% | 29.27% | 0.217% | 0.272% | 79.25MiB | 124.48MiB |
| 默认 32MiB 缓存，第 2 轮 | 23.35% | 26.46% | 0.223% | 0.281% | 93.87MiB | 124.98MiB |

三轮的检查全部通过：始终前台、2× 显示、完整输入 160 个字符、160 次滚动全部移动视口、窗口与显卡条件稳定。另有一轮 `profile32` 采集输入和滚动阶段的调用栈，仅供定位，没有并入本表。

默认两轮输入事件投递延迟 P95 为 2.49ms / 2.51ms。这个指标只描述按计划投递事件的延迟，不是屏幕显示延迟。

默认缓存两轮的滚动 CPU 平均约 26.47%。关闭屏外缓存后，滚动采样峰值约少 14.5MiB，但滚动 CPU 相对增加约 10.5%；进程历史峰值几乎没有降低。可将其作为低内存档位的候选，需要更多文档与滚动模式对照后再决定默认值。

32MiB 是图片缓存预算，并非应用总内存上限；0MiB 档仍保留当前可见行。历史峰值首次在滚动阶段采样中超过 100MiB，结合阶段顺序，滚动定位与布局值得进一步检查。当前没有分配调用栈证据将瞬时峰值归因到某一种对象。

证据：[所有性能结果及命令](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/performance/summary.json)、[构建与环境身份](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/performance/environment.json)。

## 4. 优化优先级

### A. 行号绘制：值得优先做受控对照

输入阶段的 3 秒调用栈中，`LineNumberRuler.draw` 子树有 251 次采样，`RowRenderingTextView.updateLayer` 子树有 82 次采样；滚动阶段也反复出现行号绘制、文字测量和 CoreText shaping。

行号当前每次重绘都会对可见数字执行 `size(withAttributes:)` 和 `draw(at:withAttributes:)`。可先验证复用数字尺寸、绘制属性，或少量行号绘制结果的收益。缓存应有固定上限，随字体或显示倍率变化失效，不能为全文件的每个行号建立永久缓存。

这些是包含子调用的采样数，不能直接当作 CPU 百分比，也尚未证明某项修改能降低多少 CPU。

代码：[行号测量与绘制](/Users/lee/workspace/code/textlet/Sources/LineNumbers.swift:95)。证据：[输入调用栈](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/performance/profile32.continuous-input.sample.txt)、[滚动调用栈](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/performance/profile32.continuous-scroll.sample.txt)。

### B. 等长编辑：减少主线程逐次全文摘要

普通输入改变长度时可快速判定已修改；替换相同长度内容或撤销回原长度时，仍会计算完整 UTF-8 摘要。`textDidChange()` 在主线程直接调用这一检查。

独立探针用 ASCII 正文执行 40 次单字符等长修改，摘要本身的耗时如下。编辑、显示和文件写入不计入这组 P50 / P95。

| 正文大小 | 摘要 P50 | 摘要 P95 |
| --- | ---: | ---: |
| 64KiB | 0.32ms | 0.35ms |
| 1MiB | 5.09ms | 5.22ms |
| 4MiB | 20.39ms | 20.83ms |
| 接近 8MiB | 40.65ms | 42.07ms |

这证明了随正文长度增加的主线程成本，不等于所有输入都会消耗 41ms。建议合并精确校验，校验等待期间保守标记未保存；结果绑定编辑版本，保留撤销还原后状态的正确性。后台方案也需要控制正文快照的内存成本。

代码：[输入后的文件状态检查](/Users/lee/workspace/code/textlet/Sources/Textlet.swift:646)、[完整摘要](/Users/lee/workspace/code/textlet/Sources/DocumentFile.swift:37)。证据：[摘要测量](/Users/lee/workspace/code/textlet/test-output/audit-2026-10-07/pure/final-results/pure-probes.json)。

### C. 内存：先区分缓存与存活对象，再追踪瞬时峰值

最终补充测试中，每 40 次创建/移除标签记录一次物理占用：82.57 → 83.20 → 83.27 → 83.27 → 83.27 → 83.30MiB；每一批临时对象探针均为零。当前会话仍包含三份正文及撤销历史，测试闭包也保留一个文件监听对象，所以这些数值不能解释为关闭所有文档后的空闲基线。

本轮没有发现持续保留临时标签对象的证据。暂不建议通过削减撤销能力换取占用下降。后续内存工作优先用分配调用栈检查滚动定位/布局的瞬时分配，并比较短文本、满屏文本和大文件的初始化阶段。

## 5. 建议的下一轮顺序

1. 修复恢复后删除可救回草稿的问题，并补保留正文的回归测试。
2. 修复等长、同时间戳外部替换的状态提示，继续验证显式保存的冲突保护。
3. 对行号绘制做单项优化与同条件对照；确认输入、滚动、行号显示都正确。
4. 优化大文件等长编辑的摘要调度，验证撤销、保存和恢复状态，检查快照内存。
5. 用分配调用栈追踪初始化与滚动定位峰值，再决定是否增加低内存档位。

# 逐行绘制 CPU / 内存平衡验证

本轮目标：保留逐行绘制的低内存优势，允许增加少量内存，降低真实连续输入和滚动的 CPU。最终选择 **未修改行复用 + 32MiB 图片缓存 + 纯文本 Touch Bar 格式更新优化**。这是本机、这些场景下验证过的折中，不代表所有设备、所有文档的全局最优。

## 实现

1. 缓存改用字符范围定位。监听 `NSTextStorage.didProcessEditingNotification`，修改后整段失效，后续未修改段落只平移字符位置。不会替换现有 storage delegate。
2. 行整体移动时只移动 `CALayer`。只有内容、临时样式、布局尺寸、比例或像素对齐发生变化才重新画图。
3. 未修改段落不再逐行复制 attributed string；仍检查语法高亮、输入法组合文本、下划线等临时属性。
4. 保存完整行高，不因为顶部/底部行只露出一部分而反复生成图片。屏外行按最近使用顺序淘汰，切换文档和改变容器宽度时清空；内存压力通知会释放屏外缓存。
5. 合并待执行绘制请求，避免已经完成同步绘制后再执行一次同样的排队任务。
6. 纯文本模式跳过 `updateTextTouchBarItems()` 的富文本格式状态刷新；富文本模式仍调用系统实现。表情与候选项不移除，候选更新方法不改写。

32MiB 是**可见行与屏外行的原始图片总预算**，不是额外预分配 32MiB，也不是整个应用的内存上限。可见行本身超过预算时优先保证显示。Core Animation、TextKit、撤销、草稿以及图像转换副本另占内存。

Touch Bar 判断依据：本机 SDK `NSTextView.h` 的 529–530 行把该方法定义为更新文字样式、对齐等格式控件；候选项由另一方法 `updateCandidates()` 更新。相关公开接口见 [Apple 文档](https://developer.apple.com/documentation/appkit/nstextview/updatetexttouchbaritems())。本次测试还确认表情项和候选项标识在调用前后保留。

## 测试方法与修正

- macOS 14.8.9，Intel 集成显卡，1680×940 内容窗口，2× Retina。每轮独立新草稿、独立进程；保存显卡切换计数、前台/key-window 状态、可执行文件 SHA-256 与完整原始数据。
- 240 行中文、英文、emoji 混合文本，初始 36,611 个 UTF-16 单元。通过窗口的 `NSEvent` 键盘处理路径输入 160 个 ASCII 字符；同时保留自动保存、行号等完整应用功能。
- 输入按绝对时间计划发出，默认每秒 20 次，也测每秒 10 次。程序跟不上时记录事件发送延迟，不降低目标频率来掩盖问题。
- CPU 平均值 = 阶段起止 `getrusage` 的 CPU 秒数差 / 墙钟秒数差。100% 表示一个核心，不是整台多核电脑。采样窗口 P95 只是辅助指标，窗口可能因主线程繁忙而变长，不当成固定 100ms 窗口分位数。
- 输入/滚动阶段都含最后 1 秒收尾，空闲阶段随后测 8 秒。最终驱动把定位到滚动起点的工作单列为 `scroll-setup`，避免计入空闲 CPU。
- 发现早期滚动脚本每 80 次才换方向，会撞到文档边界。最终对照每 20 次换向，并检查 **160/160 次事件都真实移动了视口**。早期与最终滚动数字不能混用。
- 小幅往返每 6 次换向，用来比较是否保留屏外缓存。
- `sample` 只在应用报告进入输入/滚动阶段后启动，采集 3 秒；采样轮只定位调用栈，不作为最终性能成绩。
- `cache0-head-1`、`cache64-head-1` 失去前台焦点，整轮排除，原始数据保留。用于排名的性能轮没有同时运行编译或其他应用性能测试；定位用的 `profile32` 不参与性能排名。

## 最终同条件结果

下面均用修正后的驱动，每秒 20 个按键、160 个输入字符、160 次真正移动视口的滚动事件。百分比以一个 CPU 核心为 100%；内存列为运行阶段的采样值，不是进程生命周期瞬时峰值。

| 方案 | 文首输入 CPU | 连续有效滚动 CPU | 输入阶段采样内存峰值 | 滚动阶段采样内存峰值 |
|---|---:|---:|---:|---:|
| 原生绘制版 | 17.4% | 33.4% | 171.4MiB | 127.9MiB |
| 修改前实验版 | 92.0% | 52.5% | 80.8MiB | 81.4MiB |
| 最终方案，第 1 轮 | 22.7% | 25.6% | 81.1MiB | 95.7MiB |
| 最终方案，第 2 轮 | 23.1% | 26.2% | 78.1MiB | 96.1MiB |

原生版作为完整应用参考，没有加入这次纯文本 Touch Bar 优化；因此不能把它与最终方案的全部差异都归因于绘制方式。

- 文首同样输入 160 个字符，CPU 工作量从 **20.11 秒**降到 **2.05–2.09 秒**，约减少 90%；包含 1 秒收尾的阶段完成时间从 **21.87 秒**缩短到 **9.04–9.05 秒**。这与“CPU 占用下降约 75%”是两个不同指标。
- 文尾输入也下降：旧实验版 **59.2% / 5.35 CPU 秒**，最终版 **22.2% / 2.01 CPU 秒**，不只优化文首场景。
- 每秒 10 次输入/滚动时，最终版分别为 **12.0% / 13.9%**；这仍是持续操作，不是把空闲时间混进来算低占用。
- 最终方案停止操作后的空闲占用约 **0.18–0.25%**，含测试采样器自身的成本。没有新增空闲轮询定时器。
- 两轮文首输入的事件投递延迟 P95 为 **2.47ms / 2.55ms**；这是按计划发出事件的延迟，**不是**屏幕显示延迟，也不是每个字符的绘制耗时。

**峰值仍需区分**：最终方案生命周期 `peakFootprint` 约 **140–144MiB**，大部分在建窗/载入密集文本的 setup 阶段已经出现；不能把“运行中约 78–96MiB”说成“任何时刻都不会超过 96MiB”。旧实验版文首轮历史峰值约 176MiB，原生版本轮约 215MiB。本次没有声称消除所有初始化瞬时峰值。

本表来自 `baseline-controlled-head`、`native-controlled-head`、`accepted-head-1/2`；补充数据为 `baseline-controlled-tail`、`accepted-tail`、`accepted-rate10`。文中数值均取对应 JSON，没有把不同版本/不同滚动脚本的数据拼成最终成绩。

另外运行完整应用的短文本/窗口缩放检查（`accepted-memory.json`）：860×590 小窗口编辑约 **15.1–15.2MiB**；1680×940 大窗口短文本编辑约 **16.7–16.9MiB**，空闲约 **16.9–17.2MiB**。此时行图片仅约 **0.07MiB**，证明没有预分配满 32MiB。这是独立的新建短草稿，不承诺已有多份草稿和历史撤销的日常会话也只有这个占用。

同一补充测试的满屏替换操作 P95 约 **4.29ms**。它包含编辑、布局与请求显示，不包含 GPU 完成，更不能解释为每输入一个中文字符的端到端延迟。

## 缓存预算选择

以下是第一步“图片复用”方案的筛选，尚未省掉每行样式复制，长滚动也还是会碰边界的旧脚本。仅在这一组内部比较缓存档，不能与最终严格滚动成绩直接拼接。

| 图片预算 | 滚动 CPU | 滚动阶段采样内存峰值 | 判断 |
|---|---:|---:|---|
| 0MiB（只保留可见行） | 20.6% | 78.1MiB | 最省内存，但往返时反复重画 |
| 32MiB | 19.6–20.8% | 93.3–94.3MiB | 增量较小，保留一些相邻行 |
| 48MiB | 19.8% | 126.7MiB | 此场景收益不足以抵偿额外内存 |
| 64MiB | 17.7% | 156.4MiB | CPU 只再降少量，接近原生版内存量级 |

之后在已省去样式复制的同一版本上，小幅往返滚动比较：0MiB 为 **28.3% CPU / 79.9MiB**；32MiB 为 **17.6% CPU / 92.6MiB**。约增加 13MiB，CPU 降约 38%。采样区间行图片重画次数由 517 降至 141。它解释了为什么最终保留少量屏外缓存，而不是只保留可见行。

## Touch Bar 波动的核实

只优化缓存时，同一输入场景曾出现约 22% 与 47% 两档 CPU。对齐输入阶段的调用栈发现 AppKit 富文本 Touch Bar 格式刷新占用显著时间。不能仅凭这些调用栈就断言全部波动都来自它，所以增加了同一可执行文件的开关对照。

最终版本恢复原生格式更新时（`control-touchbar-head`），输入 **47.4% CPU、4.29 CPU 秒**；跳过纯文本格式更新时（`accepted-head-1`），为 **22.7%、2.05 CPU 秒**。输入字符数、节奏、窗口、显卡均相同。后者的输入阶段采样区间跳过了 369 次格式刷新。

`TEXTLET_NATIVE_TOUCHBAR_UPDATES=1` 只供回归诊断，日常启动无需设置。没有关闭整个 Touch Bar，也没有修改用户系统设置。

## 正确性与范围

最终 GUI 检查共 51 项通过：缓存图片与清空缓存后的重新绘制逐像素、逐位置比较；文首插入、跨行粘贴、删除换行、窗口缩放、字体和颜色修改、语法切换、滚动返回、中文 marked text 提交、撤销重做，以及 24 次包含 emoji、组合字符、阿拉伯文、CRLF、Unicode 换行与 tab 的编辑。另检查缓存预算和 Touch Bar 项目标识。

最终可执行文件的 `--self-test`、`--syntax-test` 均通过，签名验证通过。`verification.json` 保存交付二进制 SHA-256，并核对最终性能轮确实运行的是同一二进制。已有构建警告是其他测试文件使用的 `CGWindowListCreateImage` 弃用提示，本次未引入新的构建错误。

中文输入使用 AppKit 的 marked-text / commit 接口检查，没有自动操作真实输入法候选面板。Touch Bar 验证项目保留，没有自动操作实体触控条。逐像素比较证明缓存不引入额外差异，不等同于已证明原有逐行渲染器与系统原生渲染在所有文本上完全一致。

CPU 只测本进程 user+system 时间，内存测 `phys_footprint`。未测整机功耗、WindowServer 或 GPU 显存；CPU 时间下降不能直接换算为相同百分比的续航提升。没有重新测 Sublime，也不把先前不同条件的 Sublime 数字并入本表。其他显卡、不同缩放与超大文件仍需针对性验证。

## 复现

所有原始结果位于 `Benchmarks/2026-09-28/cpu-balance/`。`baseline-renderer.swift` 保存修改前的绘制实现，`accepted-*` 是最终方案；`final32-*` 是尚未跳过 Touch Bar 格式更新的中间版本，名称不能理解为最终交付版本。

```sh
bash scripts/build-experimental.sh 'build/Textlet Balanced.app'
python3 Experiments/TextletRows/balance.py \
  --app 'build/Textlet Balanced.app' --output /tmp/textlet-new-comparison \
  --name optimized --budget 32 --scroll-span 20

# 同一套最新驱动 + 保存的旧绘制实现，隔离构建，不覆盖工作区
python3 Experiments/TextletRows/build-baseline.py \
  --renderer Benchmarks/2026-09-28/cpu-balance/baseline-renderer.swift \
  --output /tmp/TextletBaseline.app
python3 Experiments/TextletRows/balance.py \
  --app /tmp/TextletBaseline.app --output /tmp/textlet-new-comparison \
  --name baseline --scroll-span 20
```

需要桌面会话且保持测试窗口在前台。每个输出名称只能用一次，脚本拒绝覆盖已有结果。`--position middle|tail` 改输入位置，`--rate 10` 降低事件频率，`--scroll-span 6` 测小幅往返，`--profile` 仅用于诊断。

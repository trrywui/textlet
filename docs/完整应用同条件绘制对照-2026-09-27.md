# 完整应用同条件绘制对照 · 2026-09-27

## 结论

完整 Textlet 的逐行绘制版确实降低了本轮进程内存占用。在相同 Intel 集成显卡条件下，大窗口短文本编辑的采样最高值从171.50降到17.12MiB；满屏文字编辑从173.99降到78.95MiB；滚动从176.87降到80.97MiB。整轮系统记录峰值从230.65降到111.11MiB。

代价是满屏文字的CPU绘制开销增加：编辑操作P95从3.43ms增加到27.23ms，滚动P95从8.40ms增加到32.68ms。短文本编辑P95约2ms，差别较小。结果支持继续推进正式化，同时应保留旧版回退，关注密集文字编辑/滚动的响应；不能称为所有方面都更快。

## 测量方法

2026-09-27 21:19—21:21（UTC+8），依次运行原绘制版与逐行绘制版，各约55秒。两者来自同一份当前源码，原绘制使用普通构建，逐行绘制增加 `ROW_RENDERER` 编译条件。它们都包含完整应用功能，不使用此前的最小原型。

测试副本输出到 `/tmp/textlet-rendering-compare/Native.app` 与 `Rows.app`，分别采用独立的对照 bundle identifier。没有覆盖用户正在试用的 `build/Textlet Rows.app`，也没有覆盖正式版应用包。所有测试使用新建临时会话，不读取、迁移或改写用户草稿。

两者共用 `Tests/RenderingComparison.swift`，通过 `--rendering-comparison` 运行；`Sources/main.swift` 要求新建的隔离草稿目录。已验证两个构建都拒绝缺少 `--data-dir` 或含已有会话的测试请求。

- GPU：全过程 `IGPU`，`SwitchCount` 始终为 `<03000000>`。每轮运行前后及过程中约每两秒核对，合计58次记录；两轮之间计数也没有变化。
- 窗口：小窗口860×590、大窗口1680×940 points，Retina 2×。
- 字体：编辑和滚动阶段均为14pt系统等宽字体，两者记录的字体名称一致；中文由系统字体回退。加载阶段的字体记录也一致。
- 文本：相同短文本，以及180个逻辑行的中文、英文、emoji密集文本。实际输入全文保存在两个结果JSON中，程序逐字比较一致。
- 操作：小窗口编辑24次、大窗口短文本编辑54次、密集文本编辑40次、跳转滚动20次。每次编辑完成后间隔150ms，滚动完成后间隔200ms；慢帧延长阶段，不丢弃操作。
- 空闲：短文本与密集文本各停止操作11秒，窗口保持前台。
- 采样：每50ms读取本进程 `TASK_VM_INFO.phys_footprint`。两轮所有正式测量样本均为前台且测试窗口为key window。
- 全程不截图、不打开查找栏、不进行额外功能回归。用户原有实验版进程保留运行，测量只统计对应测试进程。

共同条件检查6项和两轮各5项流程检查全部通过，包括字体/尺寸一致、固定操作数、显卡稳定、前台状态、2×倍率和滚动到文末。

## 内存结果

单位为MiB（1MiB = 1,048,576字节），不是十进制MB。编辑和滚动列采用阶段采样最高值；空闲列明确使用停止操作约11秒后的末值。

| 场景 | 原绘制 | 逐行绘制 |
| --- | ---: | ---: |
| 小窗口短文本编辑，采样最高 | 36.73 | 15.62 |
| 大窗口短文本编辑，采样最高 | 171.50 | 17.12 |
| 大窗口短文本空闲，阶段末尾 | 120.81 | 17.43 |
| 大窗口满屏文字编辑，采样最高 | 173.99 | 78.95 |
| 大窗口满屏文字滚动，采样最高 | 176.87 | 80.97 |
| 大窗口满屏文字空闲，阶段末尾 | 126.95 | 79.74 |
| 整轮系统记录峰值，含窗口放大与切换 | 230.65 | 111.11 |

短文本编辑采样最高值降低约90.0%，满屏文字编辑降低约54.6%，滚动降低约54.2%。不能只报17MiB而忽略满屏文字和瞬时峰值。

原绘制的整轮峰值出现在放大窗口阶段；逐行绘制的峰值出现在密集文本滚动阶段。峰值与平时看到的“当前内存”是不同指标。本轮原绘制在11秒空闲后仍约121MiB，没有复现先前约70MiB的末值；测试流程和系统资源回收时机不同，不能把之前的70MiB混入本次对照。

大窗口短文本编辑的vmmap诊断中，原绘制的 `owned unmapped memory` 脏页约137.7MiB，逐行绘制约2.1MiB，和大块系统绘制资源减少的方向一致。这不能证明所有资源都已准确归因。vmmap是异步诊断，阶段边界触发的文件可能采到下一阶段，例如逐行版 `large-idle` 文件已包含密集文本加载；表格一律依据带明确阶段标签的进程采样，不能用诊断文件名直接替代阶段数据。

## 主线程耗时

| 场景 | 原绘制 P95 | 逐行绘制 P95 |
| --- | ---: | ---: |
| 小窗口短文本编辑 | 2.34ms | 2.40ms |
| 大窗口短文本编辑 | 2.07ms | 2.38ms |
| 大窗口满屏文字编辑 | 3.43ms | 27.23ms |
| 大窗口满屏文字滚动 | 8.40ms | 32.68ms |

时间包含同步文本修改、可见布局请求及绘制提交；逐行版包含行图片生成，系统版可能把更多绘制工作交给系统。两者都不等待GPU实际完成，因此不能把差值直接当作用户感知输入延迟，也不能据此承诺真实输入法延迟为27ms。滚动仅20次，按本测试的P95定义对应最大一次，不能当作长时间滚动分布。

本轮目的是核实内存改善，不继续修改绘制方案；运行中的试用版未变。

## 边界

这是单机、同一系统、固定顺序的一组对照，没有多轮统计置信度、长时间常驻或跨机器结论。只统计应用进程，不包含WindowServer、输入法进程或独显显存。结论是“本轮应用进程内存显著降低”，不是系统总内存固定减少90%。

用户日常试用约40MB与本轮结果并不冲突：文本密度、可见行、字体、撤销记录和系统资源回收都会影响占用。满屏密集文本仍明显高于40MB，应避免作统一上限承诺。

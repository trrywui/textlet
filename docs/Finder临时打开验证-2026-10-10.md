# Finder 临时打开验证（2026-10-10）

对应 [Issue #1](https://github.com/trrywui/textlet/issues/1)，实现基线为 `3778696ddcdf18e1413a77df12ff436923572a30`。环境为 macOS 14.8.9（23J631）、Intel x86_64、Swift 6.0.3；正式构建使用 `-O -whole-module-optimization`，目标为 macOS 14。

## 实现与系统行为

应用增加独立的 `Editor` / `Alternate` 文档声明，覆盖 `public.text` 和 `public.data`。固定文件关联列表与设置实现未改动，临时打开不调用默认应用设置 API。构建结束更新应用包目录的修改时间，使 Launch Services 能发现更新后的声明。

正常 macOS 应用服务环境中的系统查询结果如下。旧目标为已安装的旧版 `/Applications/Textlet.app`，新目标为本项目 `build/Textlet.app`。

| 文件 | 旧版系统接受 | 新版系统接受 | 新版在系统候选列表 | 默认应用保持 |
| --- | --- | --- | --- | --- |
| `.txt` | 是 | 是 | 是 | 是 |
| `.xml` | 否 | 是 | 是 | 是 |
| `.csv` | 是 | 是 | 是 | 是 |
| `.textletprobe` 自定义扩展名 | 否 | 是 | 否 | 是 |
| `Dockerfile` | 否 | 是 | 是 | 是 |
| `.env` | 否 | 是 | 是 | 是 |

系统接受性使用 `LSCanURLAcceptURL` 的 `.acceptDefault` 策略，候选使用 `NSWorkspace.urlsForApplications(toOpen:)`。未知动态类型在一级候选列表中不保证出现，可使用“其它…”选择应用；不需要为每个未知扩展名建立默认应用绑定。仅声明 `public.data` 时 `.xml` 没有进入候选列表，补充 `public.text` 后通过。系统证据见 [application-acceptance.json](../Benchmarks/2026-10-10/finder-opening/application-acceptance.json)。

**界面验证边界：** 已验证系统接受性与真实文件事件，没有自动点击 Finder 的“打开方式”菜单或“其它…”面板。已安装旧版未被替换，测试使用构建产物及唯一 Bundle ID 的隔离副本。安装新版后仍需人工核对 Finder 面板中的可选状态；本报告不将 API 查询当作界面截图证明。

## 内容与资源边界

- 普通编辑复用 `Data(contentsOf:)` 产生的原有缓冲，只借用开头至多 16KiB 检查，不复制正文或增加完整解码。已知 PDF、图片、压缩包、SQLite、OLE、ELF 与 Mach-O 签名提前拒绝；零字节和密集控制字节由既有解码结果确认是否为宽字符文本。
- UTF-8 和 UTF-16/32 BOM 沿用原有解码；原先能无损识别的无 BOM UTF-32 保持可读，保存时使用明确字节序，避免 Foundation 的通用 UTF-32 编码隐式添加 BOM。Latin-1 代表样本也保持兼容。
- 只读日志通过 `pread` 读取最多 16KiB，处理短读和 `EINTR`，错误时关闭描述符。预检在新增标签和启动索引之前完成，成功的描述符交给查看器复用。
- 8MiB 阈值保持原逻辑。日志仍拒绝 UTF-16/32 BOM，保留无效 UTF-8 的替换显示；原有 256KiB 扫描缓冲、稀疏行号索引和约 48KiB 页面未改动。
- 这是有限内容检测。测试明确保留“前 16KiB 看似文本，后部出现零字节”的 1GiB 稀疏文件能够进入日志读取器的行为。不保证识别所有二进制内容。
- 新检查只在打开读取器时执行；生产路径没有增加定时器、轮询、后台服务或按未知扩展名增长的缓存。没有追加长时间闲置测量。

## 读取器资源对照

使用同一 `Tests/TextOpeningBenchmark.swift` 驱动基线和最终源码，每例交替运行五轮、每进程先预热三次；表中为五轮中位数。普通文件为 ASCII 文本；日志探测样本有相同的 16KiB 文本开头和不同长度的稀疏尾部；二进制样本有 PDF 开头。每轮普通 16KiB / 1MiB / 8MiB 分别打开 200 / 20 / 8 次，日志 1000 次；二进制普通样本 8 次、日志样本 1000 次。测量顺序执行，与构建和 GUI 测试错开。

**范围限定为 `DocumentFile.open` 与 `LogFile.init`。** 日志耗时不包含之后的全文行号索引、搜索、窗口或绘制，不能解释为 1GiB 日志完成打开和索引仅需 0.06ms。物理占用峰值为读取器测试进程的累计峰值，包含 Foundation / AppKit 缓存和不同构建中的测试代码，并非完整应用内存，也不全是探测缓冲。

| 样本 | 单次耗时 ms：基线 → 新版 | 单次 CPU ms：基线 → 新版 | 峰值物理占用 MiB：基线 → 新版 |
| --- | --- | --- | --- |
| 普通 16KiB | 0.851 → 1.056 | 0.878 → 1.063 | 1.859 → 1.813 |
| 普通 1MiB | 7.007 → 6.940 | 7.033 → 6.799 | 9.211 → 9.281 |
| 普通 8MiB | 53.029 → 55.395 | 52.781 → 55.240 | 31.262 → 32.758 |
| 日志 16KiB | 0.0184 → 0.0579 | 0.0200 → 0.0608 | 0.840 → 1.023 |
| 日志 1MiB | 0.0172 → 0.0567 | 0.0179 → 0.0587 | 0.813 → 1.016 |
| 日志 1GiB | 0.0181 → 0.0577 | 0.0189 → 0.0603 | 0.855 → 1.090 |
| PDF 开头 8MiB | 53.826 → 1.525 | 53.822 → 1.513 | 35.270 → 8.813 |
| PDF 开头 1GiB | 0.0171 → 0.0203 | 0.0179 → 0.0208 | 0.805 → 0.898 |

日志前检增加约 0.04ms CPU，测试进程峰值增加约 0.2MiB，随总大小增长的趋势未出现。普通 16KiB 和 8MiB 的 CPU 中位数分别增加约 0.19ms、2.46ms，1MiB 略降；8MiB 耗时各轮波动约 52–59ms，不能据此承诺普通文本完全没有开销。新增扫描在代码上限于 16KiB，未增加随正文大小增长的副本。8MiB PDF 早拒绝避免了原有的解码、正文和摘要开销；1GiB PDF 对照只测读取器，基线不会在该测试中真正建立索引。

完整逐轮耗时、CPU、物理占用峰值与 RSS 见 [readers.json](../Benchmarks/2026-10-10/finder-opening/readers.json)。

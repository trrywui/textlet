# 大窗口编辑内存诊断

2026-09-27，macOS 14.8.9、Intel MacBookPro15,1、Retina 2×。使用当前工作区源码的 Release 优化构建和独立临时会话；没有修改生产源码、正式应用或真实草稿。另行编译只含系统文本控件的最小程序作对照。

## 结论

在仅 31 个 UTF-16 单元的合成文本上复现了大窗口编辑约 167MiB、小窗口约 27MiB 的差异。去掉 Textlet 的标签、行号、高亮、会话保存等全部功能，最小原生 NSTextView 程序大窗口编辑仍约 168MiB。因此本次现象的主因指向当前 macOS / AppKit / 图形驱动的窗口与文本绘制路径，而不是正文体积或 Textlet 特有功能。

这不证明系统绝无缺陷，也不证明所有原生实现都存在固定的 168MiB 下限。现有两种简单绘制改动均未解决问题；如要大幅降低大窗口编辑占用，需要进一步定位绘制资源或尝试不同渲染结构，不能承诺几行设置便可降到 30MiB。

## 实测

采样为 TASK_VM_INFO.phys_footprint，单位 MiB，约每 100ms 一次；只计被测进程，不含 WindowServer、输入法或 vmmap 子进程。窗口内容尺寸为 860×590 和 1680×940 points。各组约 53 秒，正文始终 31 个 UTF-16 单元，每 150ms 替换首字符，共约 74–76 次。正文为纯文本，无语法高亮；保留撤销。每组仅运行一次。

| 方案 | 小窗口编辑采样最高 | 大窗口编辑采样最高 | 停止编辑约17秒后 | 缩回小窗口后 | 整轮系统记录峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 当前实现 | 27.08 | 167.41 | 116.70 | 28.27 | 167.41 |
| 合并内容视图隐式图层 | 28.30 | 173.19 | 115.89 | 27.84 | 179.50 |
| 纯色图层背景并关闭滚动容器背景 | 26.43 | 159.83 | 111.73 | 23.64 | 163.88 |
| 最小原生 NSTextView | 16.17 | 167.86 | 116.66 | 17.12 | 167.87 |

当前实现在大窗口编辑阶段结束约 162.86MiB，随后回落到 116.70MiB；本轮未等待足够长时间来验证用户观察到的 70MiB。原生程序编辑区域比 Textlet 略大，其他默认控件设置也不完全相同，故它用于证明现象可以独立复现，不用于精确计算 Textlet 额外占用。

全部有效阶段采样均处于前台。运行时执行了 vmmap，采样本身会扰动进程，这不是严格的多轮性能验收。所有数据均无截图分配参与。

## 证据与解释

1. 当前实现普通 malloc 已分配量，小窗口编辑约 10.4MiB，大窗口编辑约 12.0MiB。与此同时 phys_footprint 从约 27MiB 上升至约 163MiB；主要增长出现在 `owned unmapped memory` 的脏页账目（约 1.4MiB → 136.2MiB）。这是归属本进程但不在其普通映射内的内存统计，不能单凭区域名字认定每一页都是哪种图形资源。
2. 不含 Textlet 功能的原生窗口独立复现同样增长，为窗口 / 文本绘制路径的判断提供了比单纯区域名称更强的证据。尚未获取逐个图形资源的分配栈，不能宣称已确定准确缓冲数量及每张缓冲的所有者。
3. 运行时视图树显示，`wantsLayer = false` 的 BackgroundView、NSScrollView、NSClipView 和 NSTextView 仍具有系统创建的 NSViewBackingLayer。该设置并未让本机当前绘制路径完全没有图层；有 layer 也不等于必定存在独立全尺寸位图。
4. 以 4 字节 RGBA 估算，1680×940 points、2× 的一张完整缓冲约 24.10MiB；860×590、2× 约 7.74MiB。它只是数量级说明，不是实测缓冲格式或张数。文本很少不代表窗口需要绘制的像素很少。
5. 编辑会使绘制内容发生变化；绘制中可能同时保留旧内容、新内容和合成资源。空闲后框架释放资源或将缓存改为可回收状态，可以使计入 footprint 的占用下降；本次未跟踪全部资源状态迁移，不能把每一 MiB 的回落都归因于实际释放。Apple 明确说明部分 volatile 图形资源不计入 footprint。

当前程序已有后台 `malloc_zone_pressure_relief`，但它针对分配器空闲页，不能据此要求 AppKit 正在使用的图形缓冲释放。普通堆不是本次主要增量，所以频繁执行回收、清空撤销或减少几条字符串都缺乏针对性。回落和短时稳定也不能作为“绝不存在泄漏”的证明。

## 方案与代价

- **继续保留 NSTextView：** 优先用 Instruments 的 VM / 图形资源跟踪确认编辑时新分配的表面、失效区域和缓存寿命，再逐项对照局部重绘、状态栏和行号更新、编辑区背景与图层结构。纯色背景方案只显示小幅差异，且仅一次测试，不能宣称稳定收益；合并图层本轮无效。上线前仍需验证滚动、选区、中文输入法、查找替换、日志切换和缩放外观。
- **若“大窗口编辑也必须接近30–50MiB”是硬目标：** 先做小型原型比较按可见区域分块绘制、Core Text 自绘或其他文本渲染路径。目标是减少大幅缓冲并限制同时存活的资源。不能保证换 TextKit 2 或 Metal 自动省内存。若最终放弃 NSTextView 的绘制，需要承接输入法组合文字、光标、选区、自动折行、滚动、无障碍和编辑交互等工作；窗口合成资源仍存在，因此必须先测原型再决定重写。
- **窗口缩小：** 本轮实测能直接回到约28MiB，但它改变用户使用方式，不是大窗口问题的修复。
- **降低像素倍率：** 理论上减少像素成本，但会牺牲文字清晰度或改变系统显示设置，不建议作为默认方案。本次未测试该方案。

较合理的投入顺序是先做绘制资源定位和一个最小渲染原型，使用“同尺寸、同倍率、同正文、同焦点、连续编辑和空闲恢复”的数据决定是否值得重构。当前证据支持“简单设置不足以解决”，不支持“根本不可能解决”。

## 原始数据与复现

[汇总](../Benchmarks/2026-09-27/window-memory/summary.json)、[当前实现采样](../Benchmarks/2026-09-27/window-memory/baseline.json)、[原生程序采样](../Benchmarks/2026-09-27/window-memory/native.json) 均已保留。

同目录含 vmmap、运行时视图树、诊断 main.swift、native/main.swift、纯色背景实验 patch 及生产源码 SHA-256。baseline / flatten 的 `large-settled.vmmap.txt` 是异步 vmmap 启动后紧接着缩小窗口，实际捕获小窗口，不作为大窗口空闲证据；后两组已把该快照提前到第40秒，与第43秒缩小分开。表格空闲数值来自缩小前的进程内采样。

从项目根目录构建当前实现诊断（仅临时输出，使用新建目录）：

```sh
probe_dir=$(mktemp -d /tmp/textlet-window-memory.XXXXXX)
xcrun swiftc -module-name Textlet -O -whole-module-optimization \
  -target x86_64-apple-macosx14.0 \
  -module-cache-path /tmp/textlet-swift-module-cache -framework AppKit \
  $(rg --files Sources Tests -g '*.swift' | rg -v '^Sources/main.swift$') \
  Benchmarks/2026-09-27/window-memory/main.swift -o "$probe_dir/probe"
"$probe_dir/probe" --data-dir "$probe_dir/session" \
  --probe-mode baseline --probe-output "$probe_dir/baseline.json"
```

`flatten` 模式使用同一个诊断可执行文件，但须指定另一个全新 session / 输出路径。`flat-color` 还需要将同目录 patch 应用到临时源码副本并重新编译，不能仅换模式参数就声称复现完整方案。

最小原生程序可以单独用 `swiftc -O -framework AppKit` 编译 `native/main.swift`，运行时传入 `--probe-output`。它不读写会话草稿。运行均需要可访问 WindowServer 的图形会话，诊断期间不要操作测试窗口。

## Apple 资料

- [backingScaleFactor](https://developer.apple.com/documentation/appkit/nsscreen/backingscalefactor)：每个逻辑单位对应的像素倍率。
- [canDrawSubviewsIntoLayer](https://developer.apple.com/documentation/appkit/nsview/candrawsubviewsintolayer)：合并隐式子图层可能减少内存，不保证所有情况获益。
- [wantsUpdateLayer](https://developer.apple.com/documentation/appkit/nsview/wantsupdatelayer)：直接更新图层属性的绘制方式。
- [Analyzing memory usage](https://developer.apple.com/documentation/xcode/analyzing-memory-usage)：volatile 图形资源与 footprint 的关系。

## 后续原型结果

已完成[逐行绘制实验](逐行绘制实验-2026-09-27.md)。同为 Intel 集成显卡、同尺寸、全程前台时，原型大窗口短文本编辑约11MiB、满屏编辑约42MiB；整轮峰值约54MiB。该结果证明替代绘制方式值得继续研究，但原型缺少正式编辑器功能，且多行编辑更慢。另发现独显与集显会显著影响进程内存，后续对照必须记录显卡状态。

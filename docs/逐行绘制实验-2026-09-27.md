# 逐行绘制原型实验

2026-09-27，macOS 14.8.9、Intel MacBookPro15,1、Retina 2×。本次只新增独立实验源码、构建产物与报告，未将新编辑器接入正式 Textlet，也不读写真实草稿。

## 原型

`build/RowRenderer.app` 可以直接打开输入文字。短文本与多行文本可以通过“实验”菜单切换，菜单也可查看当前进程内存。窗口标题明确标记“不自动保存”。

原型使用 Core Text 排版，将每个可见行绘制为紧贴文字宽度的图像，交给 Core Animation 合成。纯色背景不绘制全窗口位图，光标、选区与组合输入下划线独立更新。滚出窗口的行图像被丢弃；未修改的行图像复用。图像仍以2×生成，没有通过降低文字清晰度省内存。

基本编辑包括输入、退格/Delete、方向键、Shift+方向键选择、鼠标拖选、滚动、剪切/复制/粘贴、全选和撤销重做。实现 NSTextInputClient 以支持组合输入接口；真实中文输入法候选窗和拼音选词尚未端到端验证。

## 测量条件

两种模式共用应用外壳，使用相同的14pt字体、23pt行高、20pt内边距、文字内容和操作时序。系统模式是 NSTextView / NSScrollView，实验模式是自定义逐行视图。所有基准按顺序运行，使用新进程，未并行争抢焦点。

- 小窗口内容尺寸860×590，大窗口1680×940 points，均2×。
- 短文本31个UTF-16单元；多行文本180个逻辑行、30,311个UTF-16单元，包含中文、英文、emoji和自动折行。
- 每150ms替换一个字符；每50ms采样进程的 `TASK_VM_INFO.phys_footprint`，单位MiB。
- 分别记录阶段采样最高值与系统累计峰值，后者可能捕获采样漏掉的瞬时分配。
- vmmap只扫描被测进程；窗口截图在所有内存采样结束后执行。
- 编辑耗时包含修改、布局与 `displayIfNeeded` 返回，不包含GPU实际完成，不能当成端到端输入延迟。
- 只测应用进程，不计WindowServer、独显VRAM或系统整体占用；不能据此承诺系统总内存下降同样的数值。

## 必须控制显卡条件

首轮实验在AMD独立显卡驱动内屏时进行，系统输入框的进程占用也很低，无法直接拿上午集成显卡下约170MiB的数据作分母。发现这一点后，请用户自行退出当时占用独显的播放器；没有擅自终止其他应用或改变电源设置。

确认系统切回Intel集成显卡后重新对照，每次运行前后保存 `ActiveGPU` 与 `SwitchCount`。下面主要结论只使用这些集显对照。旧诊断程序的下午复测发生在显卡切换前后，且基准流程不同，单独保留但不纳入同条件结果。

不同显卡的内存模型、绘制路径和资源归属会影响进程占用。当前证据说明显卡条件是重要变量，但没有测量全部VRAM资源，不能把独显下较低的进程数字等同于机器整体更省内存，更不建议为了漂亮数字强制使用独显。

## 集成显卡下的正式对照

| 场景 | 系统输入框 | 逐行原型 |
| --- | ---: | ---: |
| 小窗口编辑，采样最高 | 35.57 MiB | 10.59 MiB |
| 大窗口短文本编辑，采样最高 | 177.46 MiB | 11.35 MiB |
| 大窗口停止编辑后，阶段末尾 | 70.61 MiB | 11.54 MiB |
| 大窗口满屏文本编辑，采样最高 | 175.27 MiB | 41.80 MiB |
| 大窗口满屏滚动，采样最高 | 176.66 MiB | 43.06 MiB |
| 整轮系统记录峰值 | 181.06 MiB | 54.10 MiB |

系统对照与本轮原型的全部采样均在前台。两组运行前后均确认为 `IGPU` 且 `SwitchCount` 未变。

`rows-igpu-1` 的短文本编辑阶段均在前台，结果约11.03MiB；但其多行阶段失去前台，因此不用于上表的满屏比较。`rows-igpu-2` 是为修正这个条件进行的补测。每个完整有效条件仍只有一轮，不能宣称长期、跨机器或跨系统版本的固定收益。

## 资源与速度

系统输入框大窗口编辑的 vmmap 显示，约149.2MiB脏页位于 `owned unmapped memory`；逐行原型对应快照约112KiB。这与避开原先的大幅绘制缓冲路径一致，但没有拿到每张系统缓冲的分配栈，不能声称已定位所有驱动资源。

原型满屏阶段同时保留约40个可见行图像，本轮估算像素载荷最高约11.85MiB；估算不包含对齐、对象、驱动副本和缓存。实际进程总占用、系统记录峰值以上表为准，不能把行图像大小当成总内存。

| 编辑场景 | 系统输入框 P95 | 逐行原型 P95 |
| --- | ---: | ---: |
| 大窗口短文本 | 2.18ms | 1.56ms |
| 30,311个UTF-16单元的多行正文 | 14.67ms | 28.65ms |

原型每次编辑仍对全文重新排版，所以多行正文更慢。现阶段验证的是渲染内存方向，不是已经完成一套全面更快的编辑器。下一步若决定接入，应先补增量排版，避免每次按键重新处理整个文档。

## 功能验证和限制

23项程序化检查通过：组合字符删除、emoji撤销重做、组合输入更新和提交、组合输入单次撤销、选区替换、候选位置坐标映射、自动折行、末尾空行、滚动淘汰行图像、可见图像上界、Shift+方向键选择与收回。截图确认中文、英文和emoji正常显示，未降低Retina倍率。截图来自首批实验，在采样结束后生成，不纳入测量。

仍缺少真实中文输入法端到端测试、生产级无障碍接口、完整系统编辑快捷键和双向文字交互覆盖。双击暂时仅选择单个组合字符。正文限制为128Ki个UTF-16单元，不支持正式Textlet的标签、查找替换、高亮、日志或草稿保存；这些功能和其内存开销都未包含在原型中。

因此可以确认“改变绘制方式有实际价值”，但不能说正式Textlet已经降至11MiB，也不能承诺所有场景低于50MB。保留原型供试用，正式编辑器继续使用原来的实现。

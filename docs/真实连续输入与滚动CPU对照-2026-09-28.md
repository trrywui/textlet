# 真实连续输入与滚动 CPU 对照（2026-09-28）

这次补测回答两个问题：快速连续输入时实验版会不会明显占用更多 CPU，以及停止输入或滚动后是否还会持续占用 CPU。

## 结论

在满屏密集文字、大窗口、Retina 2x、Intel 集成显卡的条件下，实验版确实用更多 CPU：

- 连续输入时，原版平均约占一个 CPU 核心的 **31%**，实验版约 **92%**；实验版的 P95 约 **100%**，基本会把一个核心吃满。
- 连续滚动时，原版平均约 **19%**，实验版约 **32%**；实验版的 P95 约 **73%**。
- 停止操作后，实验版输入空闲约 **0.19%**、滚动空闲约 **0.16%**；没有看到持续跑满 CPU 的情况。
- 内存方面，实验版当前 `phys_footprint` 在输入和滚动过程中约 **77–83 MiB**，原版约 **132–176 MiB**。这次正文比日常小笔记更密，绝对数不能直接等同试用时看到的 40MB，但同条件下的内存差异仍然清楚。

因此，实验版的代价主要出现在“满屏密集文字里快速连续输入”和滚动过程中；停下来以后不会一直耗电。若日常输入速度普通、试用时没有感觉到卡顿，内存收益通常值得考虑；若经常在大文本中高速输入，当前实验版仍需要继续优化绘制路径。

## 测试怎么做

原版和实验版使用同一份当前源码分别构建，均使用全新的临时草稿目录。窗口为 1680×940，倍率为 2，测试窗口全程是前台窗口和 key window，显卡记录均为 Intel 集成显卡，`SwitchCount` 没有变化。

测试先放入 240 行中英文、中文和 emoji 混合的密集文字，然后：

1. 通过窗口的 AppKit 键盘事件路径发送 160 个 key-down/key-up 输入操作，目标间隔约 50ms。
2. 停止输入后继续采样约 8 秒。
3. 通过 `NSScrollView` 的滚轮处理路径发送 160 个滚动操作。
4. 停止滚动后继续采样约 8 秒。

这里的输入事件经过目标窗口和 `NSTextView` 的事件处理路径，验证的是编辑器的输入与绘制开销；它不是物理键盘，也没有启动真实中文输入法的候选词流程，所以不能据此判断输入法候选窗的耗时。

CPU 使用 `getrusage` 统计被测应用进程的 user + system CPU 时间，每 100ms 采样一次。表中的百分比是“一个 CPU 核心”的百分比：100% 表示这个进程大致占满一个核心，不是整台电脑的总 CPU 百分比，也不是直接测得的瓦数。

## CPU 结果

| 阶段 | 原版平均 / P95 | 实验版平均 / P95 | 原版 CPU 时间 | 实验版 CPU 时间 |
| --- | ---: | ---: | ---: | ---: |
| 连续输入 | 31.3% / 50.5% | 91.9% / 100.5% | 4.12s | 24.07s |
| 输入后空闲 | 1.62% / 17.3% | 0.19% / 0.23% | 0.132s | 0.015s |
| 连续滚动 | 18.9% / 42.1% | 31.8% / 73.2% | 1.72s | 2.86s |
| 滚动后空闲 | 2.17% / 17.1% | 0.16% / 0.23% | 0.184s | 0.013s |

P95 表示 95% 的采样低于这个数，能反映偶尔出现的高负载。原版空闲阶段的平均值和 P95 受到少量保存或清理操作尖峰影响，但典型采样的 P50 只有约 0.13–0.14%；两者都没有持续后台忙等。

连续输入阶段原版约 12.3 秒完成，实验版约 25.6 秒完成。测试程序虽然每 50ms 安排一次输入，但实验版主线程在密集绘制时无法一直按这个节奏处理，因此阶段被拉长。这说明实验版的 CPU 代价是真实的；它不等于“每输入一个字固定多 20ms 的可见延迟”，但说明在这种压力下快速输入会明显挤占主线程时间。CPU 时间粗略除以 160 个输入操作，原版约 26ms/操作，实验版约 150ms/操作；这只是本次进程的平均 CPU 成本，不能当作用户每个字符必然等待的墙钟延迟。

## 内存结果

下表是每个阶段采样到的当前 `phys_footprint` 最高值和阶段结束值，不是进程历史高水位。

| 阶段 | 原版最高 / 结束 | 实验版最高 / 结束 |
| --- | ---: | ---: |
| 连续输入 | 176.2 / 131.6 MiB | 81.6 / 77.3 MiB |
| 输入后空闲 | 131.8 / 131.8 MiB | 77.3 / 77.3 MiB |
| 连续滚动 | 135.8 / 135.7 MiB | 82.7 / 81.5 MiB |
| 滚动后空闲 | 135.7 / 135.7 MiB | 81.5 / 81.4 MiB |

## 功耗能说明

CPU 使用率升高通常会让活动期间的功耗和发热上升，但本次没有用功耗计或 macOS 能源计量接口测瓦数，所以不能把 92% 直接换算成“多耗多少电”。能确认的是：实验版在快速输入期间更忙，停止操作后 CPU 很快回到接近空闲水平；长期待机功耗没有看到持续性问题。
